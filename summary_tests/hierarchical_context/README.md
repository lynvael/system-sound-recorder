# Hierarchical Context-Aware Merging (Extract-Support)

Суммаризация длинных транскриптов методом **Context-Aware Hierarchical Merging**,
вариант **Extract-Support**, по статье:

> Ou, T., & Lapata, M. (2025). *Context-Aware Hierarchical Merging for Long
> Document Summarization*. Findings of ACL 2025.
> https://aclanthology.org/2025.findings-acl.289/
> (arXiv:2502.00977)

> **Промпты** — дословные (переведённые на русский) из **Appendix A** статьи:
> Table 6 (промпт первого уровня — саммари чанка) и Table 8 (merge-промпт
> Extract/Retrieve-Support). Саммари генерируется на языке исходного текста.

## Метод

Обычный hierarchical merging работает так: текст режется на чанки, каждый чанк
суммаризируется LLM, затем саммари рекурсивно объединяются, пока не останется
один. Проблема: на каждом уровне merge LLM **не видит исходный текст**, поэтому
ошибки и галлюцинации накапливаются с каждым уровнем.

Исправление из статьи — передавать на каждом merge-шаге вместе с промежуточными
саммари **извлечённые из исходного текста отрывки (passages) как фактологическую
опору (Support)**. LLM instructed так (дословно из Table 8): суть саммари
базироваться **исключительно на приведённых саммари**, а поддерживающие
контексты использовать **только для вычитки** (proofreading) — чтобы убедиться,
что в объединённом саммари нет фактических ошибок. Контексты не подменяют
саммари и не являются источником нового содержания.

Почему **Support**, а не **Replace** (полная замена саммарий отрывками из
исходника): по результатам статьи, вариант Replace возвращает качество
«короткого» extractive-саммари и теряет связность/обобщающую способность
абстрактного саммари, тогда как Support сохраняет сильные стороны
hierarchical merging (краткость, связность, обобщение) и одновременно
снижает число галлюцинаций и потерю фактов, т.к. LLM на каждом уровне снова
опирается на оригинальный текст. Support даёт лучший баланс качество/
фактологичность без разрастания контекста.

### Извлечение Support-отрывков (extractive)

1. Разбить текст (чанка или склеенных passages) на предложения.
2. Заэмбеддить предложения (батчами по 64).
3. k-means (numpy, fixed seed, k-means++ init), `k = min(10, max(3, n//10))`.
4. В каждом кластере взять предложения, ближайшие к центроиду (interleave по
   кластерам), итого ≤ 20 предложений; восстановить исходный порядок.

## Схема пайплайна

```
исходный текст
  │  1. chunking: 32000 симв., по предложениям, overlap 500
  ▼
┌──────────┬──────────┬──────────┐
│ чанк 1   │ чанк 2   │ чанк N   │        уровень 1 (параллельно, asyncio)
│ (a) LLM  │ (a) LLM  │ (a) LLM  │  abstractive-саммари
│ (b) emb+ │ (b) emb+ │ (b) emb+ │  extractive-контекст (≤20 предложений)
│  k-means │  k-means │  k-means │
└────┬─────┴────┬─────┴────┬─────┘
     ▼          ▼          ▼
   (S1,C1)    (S2,C2)    (SN,CN)        Si — саммари, Ci — контекст
  │  2. группировка: sum(len(Si)+len(Ci)) ≤ 32000
  ▼
┌─────────────────────┐
│ merge-группа: LLM   │        уровни 2..K (рекурсия)
│ саммари + passages  │  prompt (Table 8): «объедини саммари;
│ → новая саммари S'  │  суть — только из саммари, contexts —
│ контекст C' =       │  только для вычитки»
│  emb+k-means из     │  ← контекст ВЕДЁТСЯ ИЗ ИСХОДНОГО ТЕКСТА,
│  склеенных Ci       │    а не из саммарий (механика Support)
└─────────┬───────────┘
          ▼
   рекурсия, пока не останется одна саммари
          ▼
   финальное саммари + статистика → output/<имя-входа>.md
```

Ключевая механика Support: на каждом следующем уровне extractive-контекст
получается **повторным извлечением** (эмбеддинги + k-means) из склеенных
passages предыдущего уровня, поэтому контексты всегда происходят из исходного
текста, а не из промежуточных саммарий.

## Число вызовов для N чанков

- Уровень 1: **N** LLM-вызовов (саммари) + N групп эмбеддингов
  (`⌈sentences/64⌉` HTTP-запросов на чанк).
- Каждый merge-уровень i: **G_i** LLM-вызовов (по одному на группу) + G_i
  повторных извлечений эмбеддингами.
- Итого LLM-вызовов: `N + Σ G_i`, где G_i — число групп на уровне i.
  Группировка жадная при лимите 32000 симв., поэтому дерево сжимается быстро:
  для N = 10 чанков это примерно 10 + 3 + 1 ≈ 14–16 вызовов, а не N·log N.

## Переменные окружения (`.env` в корне проекта)

| Переменная            | Обязательная | Описание                                        |
|-----------------------|--------------|-------------------------------------------------|
| `LLM_URL`             | да           | OpenAI-совместимый base_url LLM (с `/v1`)       |
| `LLM_API_KEY`         | да           | Ключ LLM                                        |
| `LLM_MODEL`           | да           | Имя модели LLM                                  |
| `LLM_REQUEST_TIMEOUT` | нет (600)    | Таймаут LLM, секунд                             |
| `EMBED_URL`           | да*          | OpenAI-совместимый base_url эмбеддингов (с `/v1`) |
| `EMBED_API_KEY`       | нет (`not-needed`) | Ключ эмбеддингов                        |
| `EMBED_MODEL`         | да*          | Имя модели эмбеддингов                          |

\* не нужны при запуске с `--fake-embeddings` (только для тестов).
При отсутствии `EMBED_URL`/`EMBED_MODEL` скрипт завершается с понятной ошибкой.

Таймауты: LLM — 600 с (из `LLM_REQUEST_TIMEOUT`), эмбеддинги — 60 с.

> **Важно про LLM-эндпоинт:** все `chat.completions.create`-вызовы обязаны
> передавать `reasoning_effort="medium"` (плюс
> `extra_body={"allowed_openai_params": ["reasoning_effort"]}` — параметр
> уже прокинут в `pipeline.py`, в `LLMClient.complete`). Без явного
> `reasoning_effort` модель отвечает неприемлемо долго (60–90+ с на вызов);
> с `"medium"` — заметно быстрее.

## Запуск

```bash
# JSON-транскрипт (список сегментов {start, end, speaker, text})
uv run python summary_tests/hierarchical_context/run.py recordings/20260924_161938/transcript.json

# TXT-транскрипт (префиксы [mm:ss] отбрасываются)
uv run python summary_tests/hierarchical_context/run.py recordings/vtb_broken/transcript.txt

# параметры
uv run python summary_tests/hierarchical_context/run.py <файл> \
    --chunk-size 32000 \          # размер чанка/merge-группы, симв.
    --overlap 500 \               # overlap чанков, симв.
    --max-context-sentences 20 \  # максимум предложений в Support-контексте
    --max-chars 20000             # обработать только первые N символов
```

В stdout — финальное саммари (на языке исходного текста) и статистика
(уровни дерева, чанки, LLM-вызовы, embedding-запросы, время); отчёт
сохраняется в `summary_tests/hierarchical_context/output/<имя-входа>.md`.

Тесты (offline, без сети):

```bash
uv run pytest summary_tests/hierarchical_context/ -v
```

## Ограничения

- **Generic embeddings вместо MemSum.** В статье extractive-отбор делается
  MemSum — моделью, обученной на суммаризацию, и её эмбеддинги ранжируют
  предложения по «важности для саммари». Мы используем generic
  embeddings-модель: кластеризация находит *репрезентативные* предложения,
  но не обязательно *самые значимые для саммари*. Это может снижать
  фактологичность Support-опоры.
- **Нет динамического выбора контекста.** Контекст извлекается целиком
  (k-means по всему объёму группы) и передаётся LLM целиком. В статье
  обсуждается (future work) context augmentation как инструмент (tool),
  который LLM сама вызывает для уточняющего извлечения нужных отрывков.
- k-means без весов/нормировки эмбеддингов; качество отбора зависит от
  выбранной embedding-модели.
