# Map-Reduce суммаризация

Экспериментальная стратегия суммаризации длинных транскриптов встреч
классическим методом **Map-Reduce**. Папка полностью self-contained:
свой загрузчик входа и свой LLM-клиент, без импортов из `app/`
и других папок `summary_tests/`.

## Метод

1. **Разбиение.** Текст делится на чанки по **32000 символов**
   (переопределяется флагом `--chunk-size`), по возможности по границам
   предложений, с перекрытием **500 символов** (`--overlap`), чтобы
   факты у границы чанка не терялись.
2. **Map.** Для каждого чанка параллельно (asyncio + `openai.AsyncOpenAI`,
   по умолчанию до 4 одновременных запросов, `--concurrency`) делается
   LLM-вызов: «составь краткое саммари, сохрани все ключевые факты (имена,
   цифры, даты, сроки, решения); отвечай на языке исходного текста».
3. **Reduce.** Саммари чанков склеиваются. Если общий объём ≤ размера
   чанка — один финальный LLM-вызов. Если больше — текст снова батчится и
   редьюсится рекурсивно (промежуточный merge-промпт), пока не останется
   одно саммари (защита от зацикливания: максимум 10 итераций). Если
   отдельное саммари само по себе не влезает в чанк, оно сначала сжимается
   отдельным collapse-вызовом.
4. **Финальный шаг.** Последний LLM-вызов всегда использует структурный
   промпт: заголовок, вступительный абзац, пунктирный список ключевых
   моментов, заключительный абзац с выводом.

Источники промптов:

- **Map** — по мотивам дефолтного map-промпта LangChain map-reduce
  (`"Write a concise summary of the following: ... CONCISE SUMMARY:"`),
  дополненный явными инструкциями по сохранению фактов.
- **Reduce (merge)** — по мотиву merge-промпта из Ou & Lapata,
  «Summarizing the Summaries» (ACL 2025).
- **Финальный (структурный)** — формат из статьи Atef Ataya о map-reduce
  суммаризации (заголовок / вступление / буллеты / заключение).
- **Collapse** — обычное сжатие с сохранением фактов.

## Вход

- `.txt` — обычный текст транскрипта.
- `.json` — список сегментов `{"start": float, "end": float, "speaker": str, "text": str}`;
  текст собирается конкатенацией `text` (speaker-метки не вставляются).

## Запуск

```bash
uv run python summary_tests/map_reduce/run.py <файл-транскрипта>
# опции:
uv run python summary_tests/map_reduce/run.py recordings/vtb_broken/transcript.txt \
    --chunk-size 32000 --overlap 500 --concurrency 4
```

Итоговое саммари печатается в stdout и сохраняется в
`summary_tests/map_reduce/output/<имя-входа>.md`.

## Сколько LLM-вызовов для N чанков

- **N чанков суммаризируются за N вызовов (Map) + 1 финальный вызов (Reduce)**
  → **N + 1 вызов**, если объём саммари чанков помещается в один чанк.
- Если склеенные саммари не помещаются: добавляется K батчей повторного
  редьюса, т.е. N + K + 1. Для типичных саммари (сжатие ~5–10×) второй
  уровень редьюса не срабатывает даже на больших транскриптах.
- Таймаут каждого запроса — 600 с (из `LLM_REQUEST_TIMEOUT` в `.env`).
- Каждый вызов делается с `reasoning_effort="medium"`
  (+ `extra_body={"allowed_openai_params": ["reasoning_effort"]}`) — без
  этого параметра модель отвечает слишком долго. Параметр вынесен в единую
  helper-функцию `llm_call()`, все Map/Reduce-вызовы идут через неё.

## Ограничения

- Качество зависит от лимита контекста модели: чанк не должен превышать
  доступный контекст минус место под ответ. 32000 символов ≈ 8–10k токенов
  для русского текста.
- Ответ каждого вызова ограничен `max_tokens=1500`: саммари длинного чанка
  может быть обрезано по середине. Если это критично, уменьшите
  `--chunk-size`, чтобы саммари одного чанка помещалось в лимит.
- Перекрытие 500 символов частично дублирует факты на границах; на этапе
  Reduce дубликаты схлопываются, но при агрессивном сжатии редкие факты
  на границе всё же могут потеряться.
- Саммари пишется LLM «по памяти»: точные цитаты и мелкие цифры могут
  искажаться; метод оптимизирован под фактологическую выжимку, а не
  дословную точность.
- Один и тот же LLM-клиент используется и для Map, и для Reduce; сетевые
  ошибки (обрыв соединения, таймаут) ретраятся 2 раза с backoff 5/15 с,
  остальные ошибки запроса роняют прогон.
- Параллельность ограничена `--concurrency`, чтобы не упереться в rate limit
  прокси. На текущем прокси (FrankAI) один запрос занимает ~3–6 минут,
  поэтому полный транскрипт на 275KB (~9 чанков) может идти десятки минут.
